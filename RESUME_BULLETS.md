# Resume bullet drafts (Alex edits these; every number is measured, source table below)

Pick 3 to 4. All timing numbers come from the clean reruns (LAB_LOG sections 28, 32, 33); perplexities from VALID runs in
results/ppl.csv and results/clean/ppl.csv (LAB_LOG 34). Ratios are ratios of medians, truncated to one decimal, never rounded up. Hardware for all: RTX 5080 16 GB, Windows + WSL2, vLLM 0.31.0, Qwen2.5 models.

1. Built a reproducible LLM-serving benchmark harness for vLLM on an RTX 5080 (idle-GPU preflight, 1 Hz GPU telemetry, fresh server
   per config, before/after canaries that reject degraded servers, interleaved repeats); measured torch.compile + CUDA graphs cutting
   median inter-token latency 1.6x to 1.9x and median time-to-first-token 33.0% to 39.0% versus eager mode on Qwen2.5-3B
   (open-loop Poisson load, 1 to 16 req/s, n=3 runs per arm).

2. Quantified quantization trade-offs on Qwen2.5 3B/7B in vLLM (n=3 runs per arm, 1 to 16 req/s): FP8 cut median inter-token
   latency 1.4x to 1.6x versus BF16 on the 3B model at +0.91% WikiText-2 perplexity (7B FP8: +0.73% vs 7B BF16; 1 run per model);
   on 7B, AWQ 4-bit had 1.4x to 1.5x lower median inter-token latency than FP8 at 1 to 8 req/s but 17.8% to 66.4% higher median
   time-to-first-token (1 to 12 req/s).

3. Implemented a continuous-batching inference engine with a paged KV cache in PyTorch (block allocator, preemption by
   recompute); against my own static-batching baseline on the same model code it cut median time-to-first-token
   37.0x to 38.7x (Poisson, 1 to 4 req/s, n=3 runs), and paged allocation used 11.7x to 12.8x fewer peak KV tokens than my own
   max-length preallocation baseline (3 runs x 3 rates).

4. Characterized an intermittent throughput stall in that engine with an interleaved A/B: with PyTorch's default CUDA allocator it
   stalled in 4 of 7 runs at 4 req/s (12.5 to 140.6 tok/s vs 318.7 to 330.8 tok/s otherwise), only in runs where continuous batching
   ran first in the process (4 of 4); with expandable segments it stalled in 0 of 7 runs. The cause is not established.

5. Measured vLLM at 2.1x to 2.9x the throughput of Hugging Face generate on Qwen2.5-3B (static batches 1 to 64, n=3 processes x 3
   trials) with identical greedy outputs (128 of 128 tokens in 6 of 6 processes), and showed the gap is decode (per-token time 2.7x to
   3.0x) rather than prefill (time-to-first-token 1.0x to 1.1x).

6. Showed that speculative decoding with a 0.5B draft model slowed a 3B target on realistic text (negative result): median time per
   output token +24.0% to +28.0% with k=3 (1, 4, 8 req/s) and +77.6% to +88.9% with k=5 (1, 4 req/s), n=3 runs per arm.

7. Measured vLLM async scheduling as a latency trade-off on Qwen2.5-3B: on (the default) it lowered median inter-token latency 4.6%
   to 6.0% but raised median time-to-first-token 28.2% to 30.2% versus off (1 to 16 req/s, n=3 interleaved runs per arm).

8. Prefix caching (best case, every prompt sharing one ~1,540-token prefix): 3.8x to 8.0x lower median time-to-first-token at
   2 to 8 req/s (n=3 runs per arm).

Not usable as results: overload / rate-16-collapse numbers, the "--max-num-seqs 128 fixes it" claim, anything TensorRT-LLM (it never
ran), the post-overload GEMV slowdown, speculative decoding at 16 req/s, the old "32 of 313 steps" stall count, and any number from
an INVALID run (this excludes the 7B AWQ perplexity, whose only run was INVALID).

### Bullet 3 features: code and tests (checked 2026-10-12)
| Feature | Implemented in | Test that covers it |
|---|---|---|
| Paged KV cache | mini_sched/kv_cache.py `PagedKVCache` (`blocks_for`, `slot`); mini_sched/model.py `PagedQwen2.step` (scatters K/V into slots, attends over each sequence's block table) | mini_sched/test_mini.py `main`: "continuous" and "preemption" checks compare greedy outputs with HF generate (end to end) |
| Block allocator | mini_sched/kv_cache.py `BlockAllocator.allocate`, `.release` | test_mini.py `test_allocator` (exhaustion raises MemoryError, double free raises ValueError); `run` asserts no blocks leaked |
| Preemption by recompute | mini_sched/scheduler.py `Scheduler._preempt` (frees blocks, resets `computed`, re-queues at the front), called from `Scheduler._schedule` | test_mini.py "preemption" check: 70-block pool, asserts `stats["preemptions"] > 0`, outputs checked against HF |
| Continuous batching | mini_sched/scheduler.py `Scheduler._schedule` (admits waiting requests while others decode; `policy="static"` admits only into an empty batch) and `Scheduler.step` | test_mini.py "continuous" check: `max_num_seqs=3`, so later requests join mid-decode |
| Token-budget scheduling | mini_sched/scheduler.py `Scheduler._schedule` (`used + n > self.budget`) and `Scheduler.add` | **none**: the test prompts total 1,313 tokens against the default 4,096 budget, so the limit never binds. Removed from bullet 3 |
